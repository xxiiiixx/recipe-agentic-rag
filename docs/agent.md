# Agent 层设计

静态 RAG 是 `query → 检索一次 → 拼上下文 → 生成`，中间没有判断。这个流程在两个地方已经实测失效：

| 失效点 | 证据 |
|---|---|
| 一次查询里放两道菜，排序由文档密度决定，弱的那道掉出 top-k | 生成评测 `cmp-009` 没召回炒青菜、`cmp-010` 没召回白灼虾 |
| 约束被解析成硬过滤后，把唯一相关的菜挡在候选集外 | 消融里 post-filter 的合规率 1.000 → 0.208 |

Agent 层不是"加个循环显得高级"，是把这两类失败变成可检测、可修复的动作。

## 图

```text
understand ──> plan ──> act ──> reflect ──(done)──> answer
                  ↑                 │
                  └──── replan <────┘  (最多 2 轮)
```

| 节点 | 做什么 | 谁来做 |
|---|---|---|
| `understand` | 拆出意图、菜名、类目、难度上限 | 规则优先，LLM 兜底 |
| `plan` | 按意图决定调几次检索、带什么约束 | 规则 |
| `act` | 调工具，把结果并入证据池 | 工具层 |
| `reflect` | 检查约束命中、实体覆盖、证据是否为空 | 规则，读结构化字段 |
| `replan` | 补检缺失的菜 / 放宽约束 / 扩大召回深度 | 规则 |
| `answer` | 带引用生成，compare 时附对照表 | LLM |

**手写而非 LangGraph**：5 个节点、一个带上限的环，不需要 checkpointer 和子图；换框架时把节点函数原样挂过去即可。取舍写在 `rag_core/agent/graph.py` 顶部。

**反思不用 LLM 判断"够了没"**：要判断的三件事（约束是否命中、compare 的两道菜是否都在、证据是否为空）都能从工具返回的字段直接读出来。交给 LLM 判断的代价是：同一 query 三遍结论不同、每轮多一次调用、答错了分不清是检索问题还是判断问题。

## 工具

| 工具 | 用途 | 静态 RAG 为什么做不了 |
|---|---|---|
| `search_recipes` | 混合检索 + 结构化约束 | — |
| `filter_by_constraints` | 按类目/难度枚举全库 | 检索只会"取前 k"，答不了"一共有多少道简单的汤" |
| `get_recipe_detail` | 取整篇或指定小节 | 命中块可能只有原料没有操作 |
| `compare_recipes` | 多篇拉成对照表 | 两篇长文混在一起，模型容易只描述其中一道 |

工具不认识状态机：只接受参数、返回结构化 dict。换编排框架时这一层不动。

## 多路检索

`plan` 按意图分流：

- `single_hop` / `constraint`：一次检索；constraint 额外枚举一次全库。
- `compare`：**每道菜单查一次**，带 `dish_names` 过滤把候选压到那道菜。
- `multi_hop`：完整查询一次 + 每个实体一次。

跨子查询的合并用 RRF（按名次，不按原始分数）：不同子查询的分数不可比，名次可比。

**枚举结果不进证据池。** 它按难度和菜名排序，没有相关性信号，混进按相关性排的池子只会把更相关的结果挤下去。它的用途是回答"一共有多少 / 都有哪些"，所以只作为答案层的补充上下文。

## 难度是偏好，不是开关

25 条 constraint 查询上试了四种策略（`scripts/eval_agent.py` 的检索深度，R@5 / 合规率）：

| 策略 | R@5 | P@5 | 合规率 |
|---|---:|---:|---:|
| 去掉难度过滤 | .339 | — | .469 |
| 固定 ≤3 | .523 | .393 | .626 |
| 固定 ≤2 | .632 | .492 | .799 |
| **≤2 过滤 + 难度升序重排** | **.695** | **.526** | **.827** |

1. **难度不能丢**：去掉后 R@5 腰斩。它是硬信息。
2. **阈值 2 最优**：语料里"简单"这个标签对应的就是 `difficulty_level=2`。
3. **重排是免费的**：不改变候选集，只把同一个集合排得更符合偏好，三项指标同时变好。实现见 `rerank_by_difficulty`。

到不了 truth 的 .747，原因不在实现：25 条查询里"特别简单"同时出现在人工标 L1 和 L2 的查询中，字面强度不预测标注阈值。gold 实际上是"满足某个隐藏元数据谓词"的菜，不是从文本能推出来的。这条写进评测集局限，不当作待修的 bug。

## 四臂对照

| 臂 | 约束来源 | 检索次数 | 反思 |
|---|---|---|---|
| `static-oracle` | 评测集给定 | 1 | 无 |
| `static-parsed` | 解析器从 query 抽 | 1 | 无 |
| `agent-plan` | 解析器从 query 抽 | 按意图多路 | 无 |
| `agent-full` | 解析器从 query 抽 | 多路 + 补检 | ≤2 轮 |

相邻两臂的差分别对应：约束解析的代价、多路检索的收益、反思环的收益。三段拆开，才知道涨的分是哪来的。

**合规率始终按评测集给定的约束判定**，不用各臂自己解析的条件 —— 否则解析器什么都不抽，合规率反而 1.0。

## 运行

```bash
# 离线冒烟：不装 torch、不连 Milvus、不调 API
python scripts/eval_agent.py --config configs/smoke.yaml --split all --out /tmp/agent.json

# 服务器真实评测
python scripts/eval_agent.py --config configs/local-hit.yaml --split test \
  --understand rules --out /backup01/caiwang/recipe-rag/outputs/agent/agent-rules.json
```

`--understand llm` 用 DeepSeek 解析，同一条 query 的解析结果会被缓存，四臂共用一份，避免把"两次解析不一致"算进臂间差异。

## 结果（105 test，2026-11-18）

bge-m3 + Milvus Lite，四臂共用同一套召回深度（融合 30 块、父文档 10 篇）与难度重排。overall 排除多跳与拒答，与检索基线同口径。

| 臂 | R@5 | R@10 | MRR | nDCG@10 | 合规率 | 工具调用 | 上下文 tokens |
|---|---:|---:|---:|---:|---:|---:|---:|
| static-oracle（评测集约束） | .920 | .974 | .900 | .902 | 1.000 | 1.00 | 1735 |
| static-parsed（规则解析） | .896 | .921 | .927 | .897 | .765 | 1.00 | 1138 |
| agent-plan（规则解析） | .899 | .924 | .924 | .905 | .764 | 1.43 | 1121 |
| static-parsed（LLM 解析） | .921 | .950 | .942 | .921 | .853 | 1.00 | 1138 |
| agent-plan（LLM 解析） | .927 | .950 | .948 | .930 | .861 | 1.57 | 1123 |
| agent-full（LLM 解析） | .927 | .950 | .950 | .931 | .861 | 1.67 | 1124 |

**收益拆开看，三个机制的贡献差一个量级。**

| 机制 | 证据 |
|---|---|
| 查询解析（实体过滤） | single_hop .943 → 1.000、compare .938 → 1.000（相对 oracle） |
| 难度重排 | 规则臂 constraint R@5 .563 → .633、整体 R@5 .876 → .896（同一解析器，只加重排） |
| 多路检索 | multi_hop R@10 .071 → .214；整体 R@10 +0.011，CI 跨 0 |
| 反思环 | 3–4 次触发，指标无变化 |

**Agent 编排的边际贡献已经很小。** LLM 解析下 agent-plan 相对 static-parsed 只有 nDCG +0.014 [+0.004, +0.026] 显著，R@5 +0.011、R@10 +0.011、MRR +0.012 的 CI 都跨 0。原因是：加了实体过滤后，compare 用单次检索就能同时拿到两道菜；加了难度重排后，constraint 的排序问题也被解决 —— 多路检索原本要修的两个问题都不在了。

**这不等于 Agent 没用，而是召回率量不到它的用处。** 对比表、全库枚举这两个工具的价值在答案层（"这两道菜哪个简单""一共有多少道简单的汤"），检索指标看不见。要证实这一点得跑生成评测，这一版没做。

**反思环如实记为无收益。** 保留它是兜底：解析出词表外的别名时，补检一次比直接放弃好。

**成本几乎不涨。** 上下文 tokens 1123 vs 1138，p50 延迟 +0.7ms。

**约束类仍未到顶**：constraint R@5 .743 vs oracle .817。差距来自难度阈值不可从文本推断（见上一节），不是实现问题。

原始结果：`/backup01/caiwang/recipe-rag/outputs/agent/agent-{rules,llm}.json`，日志同名 `.log`。

## 已知局限

- 规则解析只认闭集：类目关键词、难度词、词表内菜名。比喻式表达（"手残党也能做"）靠 LLM 臂兜。
- **LLM 解析跨运行不完全一致**：temperature=0 下两次运行仍有 4/105 条解析不同。LLM 臂的数字不完全可复现，因果结论以规则臂为准。
- 难度阈值不可从文本推断：25 条 constraint 里"特别简单"同时出现在人工标 L1 和 L2 的查询中。gold 实际是隐藏的元数据谓词，这是评测集的局限。
- 反思的补检动作只对"菜名在库、但带过滤查不到"有效；检索整体失效时，扩深度也救不回来。
- 每多一轮就多一次检索，延迟和 token 都要在报告里如实报。
