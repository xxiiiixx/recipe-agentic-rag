# 与原项目的区别

一句话：**同一份菜谱数据、沿用父子块思路，但把检索底座重写了一遍**——原实现里凡是会让实验结论失真的地方，逐条替换；原实现里正确的设计（父子块、混合检索、元数据），原样保留。

"上游"指 [datawhalechina/all-in-rag](https://github.com/datawhalechina/all-in-rag) 的 `code/C8/`（食谱 RAG 基础篇）。文中行号对应该仓库 `main` 分支 2026-10 版本。

## 1. 替换掉的十处实现

| # | 上游做法 | 位置 | 本仓库 | 为什么必须换 |
|---|---|---|---|---|
| 1 | `rglob("*.md")` 把投稿模板当菜谱 | `data_preparation.py:59` | 取数时删掉 `dishes/template`，代码不留排除规则 | `示例菜` 正文是"请在此处填写"，宽泛查询会召回它，且它永远不可能是正确答案 |
| 2 | `child_id = str(uuid.uuid4())` | `data_preparation.py:200` | `md5(parent_id ‖ section_path ‖ 序号)` | 两次建库 ID 全变，评测集无法锚定到块，只能退化到父文档粒度——父子块的价值直接归零 |
| 3 | 难度只存 `'★★★'` 字符串 | `data_preparation.py:117-123` | 另存 `difficulty_level: int`（0=未识别） | 字符串没法做范围过滤；"10 分钟内能做好的菜"这类约束查询必须能下推 |
| 4 | 先取 `top_k*3` 再后置过滤 | `retrieval_optimization.py` `metadata_filtered_search` | `SearchFilter` 下推（Milvus `filter=expr` / 本地掩码） | 条件越严，`3k` 里活下来的越少，召回随条件收紧而单调下降；且白算 3 倍 |
| 5 | RRF 用 `md5(page_content)` 当文档身份 | `retrieval_optimization.py` `_rrf_rerank` | 按 `chunk_id` 融合 | 内容哈希会把不同菜谱的同名小节（"洗净切块"）合并成一条，融合分被凭空拔高 |
| 6 | 融合分写回共享 `Document.metadata` | 同上 | 分数只存在于返回的 `ScoredChunk` | 写回共享对象后，同一批文档第二次检索带着上次的分，结果随查询顺序漂移，实验无法复现 |
| 7 | 按字符 `break` 丢弃整篇父文档 | `generation_integration.py` `_build_context` | token 预算内**文档级截断**（边界回退），`context.on_overflow: drop` 可复现上游行为用于消融 | 第 3 名一超预算就整篇消失，等于把检索排序扔了；截断至少保留开头的事实 |
| 8 | 父块回填按命中块**个数**排序 | `data_preparation.py:302-350` | `rank_parents` 支持 `rrf_sum` / `hit_count` / `max_score` | 个数排序丢弃融合分：命中两个低分块会赢过命中一个高分块，且实现是每父 ID 全量扫一遍（O(n²)） |
| 9 | `BM25Retriever` 用默认 `text.split()` 分词 | `retrieval_optimization.py` | 分词三臂：`char_bigram`（默认）/ `jieba` / `whitespace`（=上游行为） | 中文没有空格，整句被当成一个 token，稀疏路只在"查询与整段完全相等"时给分——**等于没开**（见 §2） |
| 10 | `FAISS.from_documents(...)` 进程内索引 | `index_construction.py` | Milvus 主后端 + numpy 本地后端 | 上游每次启动重建、不支持标量过滤下推；换库的真正理由见 §3，不是为了"用上向量库" |

另外两处解耦，不算缺陷但影响可测性：上游 `config.py` 把 `data_path` 写死成 `../../data/C8/cook`、`generation_integration.py` 把 `MoonshotChat` + `MOONSHOT_API_KEY` 绑在链上。本仓库把所有可变项收进 `configs/*.yaml`，一份 YAML = 一次实验。

## 2. 影响最大的一处：稀疏路等于失效

上游 `BM25Retriever.from_documents(chunks, k=5)` 走的是 langchain 默认预处理 `text.split()`。中文菜谱没有空格，一句"五花肉切块冷水下锅"整体成为一个 token，倒排表几乎不可命中。

本仓库把它做成一个可切换的消融变量，用 hashing 向量 + local 后端实测（chunk 级，gold=菜名，322 篇 / 1701 块）：

| 分词 | 有命中率 | Hit@1 | Hit@5 |
|---|---|---|---|
| `char_bigram`（默认） | 100% | 92% | 100% |
| `whitespace`（=上游） | 0% | 0% | 0% |

结论：所谓"混合检索"在上游其实是纯向量检索。修好分词后，稀疏单臂就能打到 83% Hit@1（向量臂 67%），这是本仓库第一个可讲的算法结论，也是"别把配置当结论"的实例。

## 3. 向量库：FAISS → Milvus，以及为什么还留着 numpy

换 Milvus 的算法理由只有两条，都不是"存向量"：

1. **过滤与向量检索在同一次调用完成**：先按 `expr` 求候选集，再在候选集上算距离，不存在"取 3 倍够不够"的赌注（对应缺陷 4）；
2. **标量字段可建 INVERTED 索引**：`category_key` / `difficulty_level` / `parent_id` 各自对应一类必用过滤。

同一份代码里保留 `LocalVectorStore`（numpy 内积），理由是实验效率与可复现：消融要跑几十轮，起容器 + 清 collection 会把单次迭代从 3 秒拉到 30 秒；且评测要能在没有 Docker 的机器上复现。两个后端共用同一个 `SearchFilter`，差异只剩"谁执行过滤"——所以 `filter_mode: pre/post` 的对照数能直接量化"后置过滤损失了多少召回"，这也是上游缺陷 4 的证据。

诚实的那一半：本语料只有 ~10³ 块，**只做全量 Top-k 时 FAISS 更快**。Milvus 的收益出现在"组合过滤 + 并发"下，这个结论必须用 `pre/post` 对照数说话，否则选型不严谨。

## 4. 与仓库其他章节的关系

| 章节 | 现状 | 本仓库怎么用 |
|---|---|---|
| `code/C7/agentic_rag/` | 已有 LangGraph 版 Agentic RAG（`agent.py` 21 KB）：`analyze_query → retrieve → critique → refine_query` 循环 + 最大轮次护栏 | **P2 直接沿用这个骨架**，修三处：`sub_queries` 从未被执行（拆解是假动作）、去重用 `str(hash(...))`（`PYTHONHASHSEED` 盐化，跨进程不可复现）、`critique` 的输入是整段工具输出字符串（反思对象是日志不是证据） |
| `code/C6/` | 评估骨架齐全（`BatchEvalRunner` + Faithfulness/Relevancy），但 `c6_response_eval_dataset.json` 混进生成器口水话（16 条里至少 4 条不是问题） | P1 自建 100 条评测集，指标口径借 C6，数据集不借 |
| `code/C9/` | 图 RAG + 智能查询路由（`intelligent_query_router.py` 已有 LLM 分析 + 规则降级 + 路由统计，但只统计分布、无正确性评估） | 不做图 RAG（会稀释主线）；P3 的自适应检索只借鉴它的"规则兜底"写法，且必须补路由正确率指标 |
| `Extra-chapter/` | 多模态 embedding、Neo4j 示例、PowerRAG-SDK 等旁支实践，与检索链路无关 | 不借鉴：多模态不吃文本语料，图数据库在 322 篇上过不了收益门槛 |

一句话：**仓库里不缺"能跑的 Agent"，缺的是"能证伪的实验"**。C7 的编排骨架可以抄，C6 的评估集不能抄。

## 5. 为什么不直接用 LangChain 组件

不是反对它，而是实验变量要可控：

- `MarkdownHeaderTextSplitter` 不给确定性 ID（缺陷 2 的根源）；
- `BM25Retriever` 把分词写死在默认函数里，且拿不到"候选子集内检索"的能力（缺陷 4、9 的根源）；
- 组件升级会静默改变切分与打分行为，历史实验失去可比性。

`rag_core/` 自实现 14 个模块、2341 行（含 CLI、类型标注与行内注释），换来确定性 ID、可切换分词、候选子集检索、过滤模式开关。LangChain/LangGraph 出现在 P2 的 `agent/` 层——那一层的价值是状态机与工具协议，不是文本切片。
